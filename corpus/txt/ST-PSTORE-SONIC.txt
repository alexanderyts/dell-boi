Introduction
This deployment guide covers Dell Technologies PowerSwitch configuration using SmartFabric Manager for SONiC (SFM) for single rack or multirack greenfield PowerStore nonvolatile memory express (NVMe)/TCP storage deployments. SFM automates the configuration of the leaf-spine fabric that is used in this deployment. The leaf-spine fabric uses Virtual Extensible LAN (VXLAN), which enables a virtual Layer 2 overlay network to run over a physical Layer 3 underlay network. Use of a VXLAN leaf-spine fabric is a best practice in the data center.
Topics:
• Enterprise SONiC Distribution by Dell Technologies • SmartFabric Manager for SONiC • PowerStore • Typographical conventions • We value your feedback
Enterprise SONiC Distribution by Dell Technologies
SONiC is an open-source, Linux-based network operating system that runs on switches from multiple vendors and ASICs. Enterprise SONiC Distribution by Dell Technologies is a hardened and validated version of SONiC that is supported on Dell PowerSwitch platforms. Dell Enterprise SONiC supports an intuitive command-line interface, object-based administration through a REST interface, Google’s gRPC Network Management Interface (gNMI), and simplified configuration using SmartFabric Manager.
SmartFabric Manager for SONiC
SmartFabric Manager for SONiC (SFM) simplifies network configuration and maintenance by automating network deployment and providing an easy-to-use web user interface. SFM is a virtual machine that runs on VMware ESXi, provided in OVA format, or on Linux KVM, provided in QCOW2 format. SFM configures Dell PowerSwitch systems using REST API commands. The PowerStore deployment in this guide uses a Border Gateway Protocol (BGP) Ethernet VPN (EVPN) with VXLAN leaf-spine fabric. VXLAN enables a virtual Layer 2 overlay network to run over a physical Layer 3 underlay network. Use of a VXLAN leaf-spine fabric is a best practice in the data center. Manually configuring the switches for this fabric would require hundreds of CLI commands. SFM automates the fabric creation, making it fast, easy, and with a much lower probability of errors than configuring the fabric manually. SFM comes with a 180-day free trial for up to 10 switches. If your deployment uses more than 10 switches in leaf or spine roles, you must buy a license before proceeding. See the SmartFabric Manager for SONiC User Guide for more information about licensing.
PowerStore
Built for NVMe technology, PowerStore uses a dual-node appliance architecture that features an active/active controller configuration where both nodes service I/O simultaneously. PowerStore can scale up with single-drive granularity to over 1 PB raw storage capacity per appliance. PowerStore can also scale out to four appliances per cluster.

Topology
The topology for this deployment is divided into two parts: 1. Production, or in-band 2. Out-of-band (OOB) management The production topology contains redundant components and is used for all mission-critical and end-user network traffic. The OOB management network is an isolated network for hardware and PowerStore appliance management.
Topics:
• Production topology • Production topology connection details • OOB management topology • OOB management connection details

The production topology that is used in this guide is shown in the figure below.

VXLAN is used to stretch Layer 2 networks across the Layer 3 leaf-spine fabric. Equal-Cost Multi-Path routing (ECMP) is enabled on the switches to use all available bandwidth on the leaf-spine connections. SFM automates the configuration of this VXLAN fabric.
NOTE: See BGP EVPN with VXLAN overview in the appendix for more information.
Two leaf switches are used in each rack for redundancy and performance. A multichassis link aggregation group (MC-LAG) peer link connects each pair of leaf switches. Every leaf switch is connected to every spine switch to form a leaf-spine topology.
PowerStore appliances that are in the same PowerStore cluster can be in the same rack or in different racks as shown in the figure above. PowerStore cluster network connections, which are shown in blue, use Link Aggregation Groups (LAGs) with Link Aggregation Control Protocol (LACP). If there is only one PowerStore appliance, the PowerStore cluster links shown are not required.
The PowerStore appliance and storage client NVMe/TCP connections, which are shown in green, do not use LAGs in this deployment. There should be at least one NVMe/TCP connection from each PowerStore appliance node and storage client to each leaf switch in the rack for redundancy.
Storage clients can be any PowerEdge or third-party server with at least two 25 GbE or faster NICs. The client operating system must support NVMe/TCP.
NOTE: The example that is detailed in this guide uses two spine switches and the equipment that is shown in Racks 1 and 2 in the figure above. The figure shows how the topology can be scaled out to include additional switches and racks.

It can also include other devices using their dedicated management ports. One S3248T-ON switch is typically installed in each rack for OOB management network connections, as shown in the following figure. Other Dell and third-party switches with 1 GbE BASE-T ports can also be used for OOB management traffic.

Figure 8. OOB management network topology

If PowerStore appliances are in different racks, you can keep them in the same VLAN by using Layer 2 uplinks to the OOB management network core switch. If you use Layer 3 uplinks to the OOB management network core switch, connect all PowerStore appliances to the same physical OOB management switch, even if the appliances are in different racks.

Minimum networking requirements
NOTE: In this guide, “single rack” means topologies with only two leaf switches. “Multirack” means topologies with four or more leaf switches.
The minimum networking requirements for PowerStore deployments with SFM include the following:
● Single rack deployments require two supported Dell PowerSwitch leaf switches of the same model. ● Multirack deployments require two supported Dell PowerSwitch leaf switches of the same model per rack, plus at least two
supported Dell PowerSwitch spine switches. ● All Dell PowerSwitch leaf and spine switches in the fabric must be running the same version of Dell Enterprise SONiC.
(Temporary exceptions are allowed during SONiC OS upgrades.) ● Dell Enterprise SONiC 4.4.1 or later with an Enterprise Standard or Enterprise Premium bundle is required on all leaf and
spine switches in the fabric. ● At least one 1 GbE BASE-T switch is required for OOB management connections. Dell Technologies recommends using one
PowerSwitch S3248T-ON per rack. If Dell PowerSwitches are used for OOB management, Dell Technologies recommends Enterprise SONiC 4.4.1 or later with the Lite bundle. ● Each PowerStore appliance requires at least one 25 GbE SFP28 or faster connection to each leaf switch in the rack for NVMe/TCP storage traffic. As a best practice, do not use a link aggregation group (LAG) for NVMe/TCP connections. ● If multiple PowerStore appliances are used in a cluster, each PowerStore appliance requires two additional 25 GbE or faster connections to each leaf switch in the rack for cluster traffic. These connections must be in a LAG with Link Aggregation Control Protocol (LACP) enabled. ● MC-LAG peer links between leaf switch pairs require at least two connections for fault tolerance. Dell Technologies recommends using 100 GbE or faster ports for these connections. If 25 GbE ports are used for the peer link, Dell Technologies recommends using at least four connections for sufficient bandwidth. ● One 1 GbE (1000BASE-T) connection is required for each OOB management port on leaf and spine switches. ● One 1 GbE (1000BASE-T) connection is required for each of the two OOB management ports on PowerStore appliances. ● If PowerEdge servers are used as storage clients, one 1 GbE (1000BASE-T) connection is recommended for each server’s iDRAC port. ● One server running ESXi 7.0 or later or Linux KVM is required to host the SFM VM. The SFM VM requires at least 32 GB RAM, 120 GB free disk space, and 16 virtual CPUs. In addition to the server’s iDRAC 1 GbE (1000BASE-T) connection, the host server must have a network connection that allows the VM to reach the OOB management network. SFM uses this connection to communicate with the leaf and spine switches.

Configure OOB management switches
This section shows an OOB management switch configuration example. It uses a Dell PowerSwitch S3248T-ON running Dell Enterprise SONiC 4.4.1 Lite. The switch starts at its factory default configuration.
NOTE: OOB management switches can be Dell PowerSwitch systems or third-party switches with 1 GbE BASE-T ports. If you are using an operating system other than Dell Enterprise SONiC, refer to your operating system’s documentation for specific commands. 1. Connect to the switch using the console serial port. 2. Log in to the CLI using the default username admin and password YourPaSsWoRd. 3. Change the admin password to a secure one when prompted. 4. Run the following commands to use standard interface names and to set the hostname. admin@sonic:~$ sonic-cli sonic# configure terminal sonic(config)# interface-naming standard Broadcast message: Interface naming mode has changed. Users running 'sonic-cli' are required to restart your session. sonic(config)# hostname S3248T-OOB Broadcast message: Hostname has been changed from 'sonic' to 'S3248T-OOB'. Users running 'sonic-cli' are suggested to restart your session.
5. Exit to apply the changes and return to the SONiC CLI. sonic(config)# exit sonic# exit admin@sonic:~$ sonic-cli S3248T-OOB#
6. Enabling a spanning tree protocol is a best practice. Rapid per-VLAN spanning tree is enabled in this example. S3248T-OOB# configure S3248T-OOB(config)# spanning-tree mode rapid-pvst
7. Create the OOB management VLAN. S3248T-OOB(config)# interface Vlan 100
NOTE: VLAN ID 100 is an example. Any available VLAN ID can be used.
8. Configure all downlink ports that will be connected to PowerStore management ports, PowerEdge server iDRACs, and other devices in the rack if applicable. Put them in the same VLAN as access (untagged) ports and bring the ports up administratively. S3248T-OOB(config)# interface range Eth 1/1-1/48 %Info: Configuring only existing interfaces in range S3248T-OOB(config-if-range-eth**)# switchport access Vlan 100 S3248T-OOB(config-if-range-eth**)# no shutdown
9. Configure the uplink to the OOB management network core switch. Details are not shown here as the uplink can be configured using different Layer 2 or Layer 3 options. If the uplink is in Layer 3 mode, all PowerStore appliances in a cluster must be connected to the same OOB management switch (see note below).

Prepare leaf and spine switches for SFM
Set the admin password and configure the management interface
For each Dell PowerSwitch that will be a leaf or a spine in the fabric, do the following: 1. Connect to the switch using the console serial port. 2. Log in to the CLI as admin. 3. Change the admin password from the default, YourPaSsWoRd, to a secure password during the first login when prompted. 4. Configure the OOB management interface (Management 0). SFM uses this interface to communicate with the leaf and spine
switches. For SFM, Dell Technologies recommends using a static IP address instead of DHCP on Management 0 to ensure that it does not change. If routing is used on your OOB management network, also specify the gateway address as shown in the configuration example below.
admin@sonic:~$ sonic-cli sonic# configure sonic(config)# interface Management 0 sonic(config-if-Management0)# ip address 100.67.112.13/24 gwaddr 100.67.112.254 sonic(config-if-Management0)# end sonic# write memory
The commands above are the only ones that are required at the switch CLI when using SFM. The IP addresses used are examples only.
NOTE: If any leaf or spine switches have previously been configured (other than changing the admin password and configuring Management 0), run the write erase command and reboot each applicable switch. The admin password and Management 0 interface configuration will be retained. All other configuration settings on the switch will be reset to the factory defaults.
Connect the switches and SFM host
Make the switch and SFM host connections as shown in Production topology connection details and OOB management network connection details. The PowerStore appliances and storage clients do not have to be connected now. Deploy the SFM virtual machine to a VMware ESXi or Linux host as shown in the SmartFabric Manager for SONiC User Guide. SFM is available in OVA format for ESXi or in QCOW2 format for Linux KVM.

BGP EVPN with VXLAN overview
BGP EVPN with VXLAN stretches virtual (overlay) Layer 2 networks across a physical (underlay) Layer 3 leaf-spine fabric. This architecture allows for the scalability of Layer 3 networks with the mobility benefits of a Layer 2 network. For example, a VM or physical host can be moved from one rack to another without the need to change its IP address and gateway information. All paths in the fabric are active and no connections are blocked by the spanning tree protocol. EVPN uses BGP to exchange endpoint MAC and IP address information between VXLAN tunnel endpoints (VTEPs). In this topology, each pair of leaf switches in a rack is one logical VTEP. Packets destined to a remote device are sent to the local VTEP as the first hop. The packet is encapsulated with a VXLAN header that includes the Virtual Network Identifier (VNI) and the IP address of the destination host. See the figure below.

Figure 42. VXLAN encapsulated frame
The destination VTEP extracts the original packet and routes it to the destination. VXLAN encapsulation adds approximately 50 bytes of overhead to each Ethernet frame. As a result, all switches in the underlay (physical) network must be configured to support an MTU of at least 1600 bytes on all participating interfaces.
NOTE: In this deployment, switch interfaces are automatically set to their maximum supported MTU size of 9216 bytes by SFM for best performance.
Anycast gateways with the same IP address are configured on each leaf pair. An anycast gateway IP address is set as the default gateway for hosts and VMs on that virtual network. Hosts and VMs on the same virtual network use the same gateway address while behind different leaf pairs. This configuration replaces the Virtual Router Redundancy Protocol (VRRP) and enables hosts and VMs to migrate from one leaf pair to another without changing the network configuration.
