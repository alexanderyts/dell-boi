Deployment Introduction
Document overview
The Dell AX Solutions for Microsoft product family includes: ● Dell AX System for Azure Local (based on Azure Stack HCI operating system) ● Dell AX System for Windows Server (not described in this guide) This end-to-end deployment and operations guide provides an overview of Dell AX System for Azure Local with scalable networking. The guide includes: ● Guidance on how to integrate solution components ● Instructions for preparing and deploying the solution infrastructure
NOTE: This guide only applies to infrastructure that is built using the validated and certified AX nodes from Dell Technologies and the Azure Stack HCI operating system.
Audience and scope
The audience for this document includes systems engineers, field consultants, partner engineering team members, and customers with knowledge about deploying hyperconverged infrastructures (HCIs) with the Azure Stack HCI operating system, Hyper-V, and Storage Spaces Direct. Customers who do not have Volume License agreements with Microsoft can order AX nodes from Dell Technologies with a factory-installed operating system and OEM license or as a bare-metal installation. An Azure Local instance can be deployed in the following ways: ● Dell Technologies Services-led—Certified deployment engineers ensure accuracy, speed, and reduced risk and downtime. ● Customer led—Customers who have the qualified level of technical expertise follow the instructions in this guide.
Assumptions
This guide assumes that deployment personnel understand the following technologies and tasks: ● AX nodes from Dell Technologies ● Deploying and configuring BIOS and integrated Dell Remote Access Controller (iDRAC) settings
Known issues
Before starting the cluster deployment, see Azure Local release information.

Solution Overview
Solution introduction
Dell AX System for Azure Local includes various configurations of AX nodes from Dell Technologies. AX nodes power the primary compute cluster that is deployed as a hyperconverged infrastructure (HCI). The HCI uses a flexible solution architecture rather than a fixed component design. For information about supported AX nodes and operating-system support for each of the AX nodes, see the Azure Local Support Matrix. The solutions are available in both hybrid and all-flash configurations. For more information about available configurations, see the Dell AX System for Azure Local specification sheet.
Deployment models
Dell AX System for Azure Local offers the following types of cluster infrastructure deployments: ● Switchless storage networking ● Scalable infrastructure
Scalable infrastructure
The scalable offering for Dell AX System for Azure Local encompasses various AX node configurations. In this Azure Local solution, as many as 16 AX nodes power the primary compute cluster. The following figure shows one of the flexible solution architectures. It includes the Azure Local instance, redundant top-of-rack (ToR) switches, a separate out-of-band (OOB) network, and an existing management infrastructure in the data center.

Dell AX System for Azure Local does not include:
● Management infrastructure components such as a cluster for hosting management virtual machines ● Services such as Microsoft Active Directory, Domain Name System (DNS) ● Microsoft System Center components such as Operations Manager (SCOM)
The instructions in this guide do not include deployment of any of these services and components, and they assume that at least an Active Directory domain controller is available in the existing management infrastructure. In a remote office scenario, Dell Technologies recommends that you deploy either an Active Directory replica or read-only domain controller (RODC) at the remote office. If you are using an RODC at the remote site, connectivity to the central management infrastructure with a writable domain controller is mandatory during deployment of the Azure Local instance.
Top-of-rack (ToR) switches that are used in Azure Local instance deployments and that forward RDMA storage-network traffic must be listed in the Azure Local ToR switch list on the following Microsoft page: Physical network requirements for Azure Local > Network switches for Azure Local
NOTE: For deployments with ToR switches that are not listed, you must use the switchless storage-network deployment option.

Solution integration and network connectivity
Each of the variants in Dell AX System for Azure Local supports a specific type of network connectivity. The type of network connectivity determines the solution integration requirements. For sample switch configurations for these network connectivity options, see Switch Configurations – RoCE/iWarp (Mellanox and Intel E810 Cards) Reference Guide or Dell Technologies Enterprise SONiC with Azure Local.
NOTE: Data Center Bridging (DCB) is required for all Azure Local instance deployments.
Adapter requirements
Azure Local requires using the same adapter card vendor and model for the machines in an instance that supports instance operations. The ports that are used by the same Network ATC intent must use the same vendor, model, and speed. Starting with Azure Local Solution version 2603, Azure Local instances that require NIC-level high availability can use the Azure portal or ARM templates to configure Network ATC intents using NIC ports from adapters that share the same PCIe Vendor ID and PCIe Device ID. This capability enables ports from both an OCP NIC and a PCIe riser NIC to be included within a single Network ATC intent, provided the adapters are of the same NIC model.
CAUTION: If you use optics or cables from one vendor with an adapter card from another vendor, Dell cannot guarantee that your configuration will work as expected. Before you mix vendor equipment in an Azure Local instance, consult the Dell Technologies cable and optics in the Support Matrix.
Fully converged network connectivity
In the fully converged network configuration, both storage and management or VM traffic use the same set of network adapters. These adapters are configured with Switch-Embedded Teaming (SET). When using RoCE in a fully converged network configuration, you must configure DCB. The following figure depicts the integration of the fully converged architecture.

Registering a Partner Admin Link (PAL) for Azure related solutions
Partner Admin Link (PAL) is a simple telemetry-based capability that is built into Microsoft Azure. PAL enables Microsoft to track partner involvement in Azure related technical engagements. Adding a Dell Partner ID to the Service Principal does not provide Dell with additional access to the customer system and does not change any Azure Role-Based Account Controls (RBACs).
NOTE: Adding a Dell Partner ID to the Service Principal associates Dell to the customer entity, which is persistent. This means that changes in customer system administrators do not break this association. Dell Technologies employees can add a PAL using the user ID associated with either the subscription or Service Principal that is used for Arc or for Azure Local registrations. During a deployment, the customer creates the Service Principal for their system. Dell Technologies recommends that you use the user ID associated with the Service Principal for the registration as described in Add a PAL through the Azure portal by using Azure PowerShell with Service Principal user ID. Alternatively, you can follow the procedure that is described in Add a PAL through the Azure portal using the subscription user ID.

Configuring network switches
Top-of-rack (ToR) switches that are used in Azure Local instance deployments and that forward RDMA storage-network traffic must be listed in the Azure Local ToR switch list on the following Microsoft page: Physical network requirements for Azure Local > Network switches for Azure Local.

To enable storage and VM or management traffic, you can configure the top-of-rack (ToR) network switches based on the selected network topology.
Management network redundancy is a combination of either iDRAC or operating system DNS/IP resolution.
NOTE: Dell Technologies recommends that you deploy a network topology that supports a dual-control plane while sharing a single-data plane. Virtual Link Trunking (VLT) is a Dell Technologies proprietary technology that provides network resiliency for data I/O.
You should size any solution before making a decision on the bandwidth of the SMB switch to be used.
NOTE: If you are using an All-Flash or All-NVMe solution, Dell Technologies recommends that you use 25 GbE or higher switches for SMB traffic.
Configuring switch VLT redundancy with Virtual Router Redundancy Protocol (VRRP) provides a virtual floating IP address that any machine can reference as a gateway. If a switch fails, the virtual IP address is transferred to a peer switch.
VRRP is an active/standby, first-hop redundancy protocol (FHRP). When used with VLT peers, VRRP becomes an active/active protocol. The VRRP virtual MAC address is the local-destination address in the forwarding information base (FIB) table of both VLT peers. Using this method, the back-up VRRP router forwards intercepted frames that have a destination MAC address that matches the VRRP virtual MAC address.
A standard Storage Spaces Direct deployment requires the following basic network types:
● OOB management ● Host management ● Compute ● Storage
The number of network ports (two or four) that are used in the storage configuration determines whether you have two or four fault domains.
For sample switch configurations, see Switch Configurations – RoCE/iWarp (Mellanox and Intel E810 Cards) Reference Guide.

About Local Identity with Azure Key Vault

Overview

Azure Local can be deployed without Active Directory by using a local identity model with Azure Key Vault, previously known as AD-less deployment. This deployment option is available starting with Azure Local version 2411 and later.
In a local identity deployment:
● A dedicated local administrator account is used on each machine. ● Certificate‑based authentication is configured cluster‑wide. ● Azure Key Vault is used to securely back up secrets such as BitLocker keys and other critical configuration data that is
required for secure cluster operation.

Benefits of local identity with Azure Key Vault (without Active Directory)
● Minimal edge infrastructure: Enables secure identity and secret handling in environments that do not use Active Directory. ● Secure secret store: Azure Key Vault stores sensitive items such as BitLocker keys and node passwords, reducing the risk of
unauthorized access and improving overall security. ● Simplified management: Consolidates deployment and local identity secrets in a single vault, making them easier to manage
and retrieve. ● Simplified deployment: Azure portal workflows store required secrets in Azure Key Vault, reducing reliance on Active
Directory and helping simplify Operational Technology network firewall configurations.
Most deployment steps are identical for Active Directory–based Azure Local deployments and deployments that use local identity with Azure Key Vault. For more information, see Deploy Azure Local using local identity with Azure Key Vault.

Storage Spaces Direct storage expansion
In an Azure Local instance, expanding storage by adding drives on the available slots on the instance machines adds storage capacity to the instance and improves storage performance. Before the storage expansion, ensure that all drive types and the amount in each drive are the same and are equal to that of the drive in use. Do not combine different drive types in the same Azure Local instance or machine. For example, you cannot combine SATA and SAS hard drives or solid-state drives. The following options for expanding the storage capacity of the cluster are supported: ● Option 1: Expand the storage with the same drive manufacturer, capacity, endurance, latest model, and latest firmware.
Determine if the drive is available on the AX node model that is listed in the Support Matrix. ● Option 2: Expand the storage with a different drive manufacturer, model, firmware, and the same capacity and endurance.
Determine if the drive is available on the AX node model that is listed in the Support Matrix. When drives are added to extend the overall storage capacity per machine, the Azure Local instance starts claiming the hard drives into an existing storage pool. After the drives are added, they are shown as available for pooling (CanPool is set to True) in the output of the GetPhysicalDisk command. In a few minutes, the added drives are claimed in the existing pool, and then Storage Spaces Direct starts the rebalance job. FullPowerCycle
FullPowerCycle is a calling interface function that provides a way to reset the server auxiliary power. An increasing amount of server hardware runs on server auxiliary power. Troubleshooting some server issues requires you to physically unplug the server power cable to reset the hardware running on auxiliary power. The FullPowerCycle feature enables the administrator to connect or disconnect auxiliary power remotely without visiting the data center. This feature is supported on AX nodes and on Storage Spaces Direct Ready machines. The relevant commands to run in the PowerShell console are: ● To request FullPowerCycle on your system: Invoke-FullPowerCycle -status request ● To get the status of FullPowerCycle on your system: Invoke-FullPowerCycle -status Get ● To cancel FullPowerCycle on your system: Invoke-FullPowerCycle -status cancel

Secure connect gateway
Secure connect gateway (SCG) is an enterprise monitoring technology that is delivered as an appliance and a stand-alone application. It monitors your devices and proactively detects hardware issues that may occur. Depending on your service contract, it also automates support request creation for issues that are detected on the monitored devices. When a hardware issue is detected, SCG automatically collects the telemetry that is required for troubleshooting the issue. The collected telemetry helps technical support to provide a proactive and personalized support experience. For more information about SCG, see Secure Connect Gateway - Application Edition.
