# Backtest 2026-07-16 — dual-NIC 2-rack design (Run 2 revision)

**Defect meter: 0 → 2 → 0, same day.** R2 and R5 were real defects on a *shipped*
BOM (a silent per-fabric mechanism split; a header that hid a selected NIC), so the
meter honestly rose to 2 when they were found and returned to 0 when they were fixed
the same day. Found-and-fixed-fast is the meter's credibility — recorded as a
movement, not smoothed over as "stayed at zero."

## The design (corrected input)

The maintainer re-ran the design and confirmed a **second NIC was selected** in
the wizard that the first pass missed:

- ~40× PowerEdge general-purpose servers, 2 racks, dual (redundant).
- **NIC 1:** Broadcom 2-port **10GBase-T** (frontend).
- **NIC 2:** Broadcom 2-port **1GBase-T** (frontend).
- → **4 ports/server, 160 host links, two frontend fabrics** (80 links each).

This correction is why R1 and R4 (below) are **withdrawn**: the hardware sizing
was correct all along — it only *looked* wrong because the BOM header
under-reported the input (see R5). **The false-alarm reasoning is logged here
deliberately: a summary that under-reports the configuration is itself a
defect, because it makes correct hardware look like an over-count.**

### R5 — input-summary accuracy (FIXED)

**Was:** the BOM header printed `NIC 1× Broadcom 2-port 10GBase-T = 2 ports/unit`
for a 4-port/server design — the second NIC was invisible anywhere on the
output. The maintainer selected it in the wizard and could not find it, which
nearly produced a false over-count report (R1/R4).

**Ruling (maintainer):** NICs are quoted with the **server configuration**, not
by this network BOM — but the demand source must be **visible** so the
dependency is explicit.

**Fix:**
1. The header now lists **every** NIC with the true total ports/unit
   (`1× Broadcom 2-port 10GBase-T … + 1× Broadcom 2-port 1GBase-T … → 4 ports/unit`).
2. Each NIC gets an **unpriced reference line** in the BOM:
   `(Reference) 40× Broadcom 2-port 1GBase-T NIC — quoted with the server
   configuration, NOT this network BOM; if the server quote changes NICs, re-run
   this.` — so if a NIC is dropped from the server quote, the dependency on the
   network BOM is explicit.
3. **New invariant (INVARIANT 5, tests/invariants.js):** every host-driving NIC
   in the input appears in the output (header + reference line) — a SIZING input
   that affected the design can never be silently omitted from the summary again.

### R2 — ICL quantity + per-fabric note (RULING NEEDED)

**Reported:** ICL line qty 8 with a note enumerating only 4 + `+more` — a
cross-fabric merge whose note should read "8 total — 4× 10G fabric, 4× 1G
fabric" per DERIVATIONS §1.

**What the current build actually produces (post-B4 increment):** the ICL is
**qty 4, with a clean note, no merge.** Only the **primary** (per-rack) 10G
fabric builds an MC-LAG peer-link; the secondary 1G fabric uses **EVPN-Multihoming**
(all-active, no peer-link) — a valid, port-cheaper redundancy that builds no
second ICL. So the qty-8 merge the reviewer saw **no longer reproduces** — the
B4 ICL-feasibility work changed it.

**Why the line would "escape canonical note generation":** confirmed
architectural gap — `js/design.js applyCanonicalBom` regenerates the switch,
`host|` and `uplink|` lines, but **not `peer|` (ICL) lines**. So *if* two ICLs
ever merged, the note would stay stale (`+more`). With current perRack logic
(only the primary fabric is per-rack) two `peer|` lines cannot share a merge key,
so the gap is real but **not currently triggered**.

**Diagnostic (maintainer asked: port-driven or policy?):** the secondary's EVPN-MH
was **POLICY-driven, not port-driven.** `perRack` was gated on `fs.isPrimary`
(engine.js), so only the primary fabric was a per-rack ToR pair → MC-LAG; the
secondary fell through to the `else → evpn-mh` branch purely because it wasn't the
primary — NOT because `fs.iclFits` was false. That is exactly the silent policy
substitution the override-warn precedent forbids.

**Ruling (maintainer):** both fabrics MC-LAG (qty 8) — the input was "MC-LAG
pair", and a silent per-fabric mechanism split reverses the override-warn
precedent. EVPN-MH stays **fallback-only** (port infeasibility + WARN), never a
silent policy.

**Fix:**
1. **Removed the `fs.isPrimary` gate on `perRack`** (engine.js): every data fabric
   of a rack-spanning target is now a per-rack ToR pair (back-end A/B excluded).
   So both fabrics are MC-LAG (4 ICL each = 8). Leaf counts are unchanged (both
   fabrics were already 4 leaves), so R1/R4's withdrawal still holds. EVPN-MH is
   now reachable only via the port-infeasibility fallback (`fs.iclFits === false`
   + WARN) — never as a silent per-fabric policy.
2. **Closed the canonical gap:** `js/design.js` `buildCableList` now produces
   `peer|` (ICL) records, and `applyCanonicalBom` regenerates the merged note per
   DERIVATIONS §1 — it reads:
   `MC-LAG ICL — 8 total across 2 fabrics on the same servers: 4× 10GBase-T
   fabric, 4× 1GBase-T fabric (each a 100GbE peer-link …)`. No `+more`.
   Regression-guarded in `tests/unit-engine.js`.

### R3 — OOB inter-rack aggregation note cites a removed spine rack (RULING NEEDED)

**Is:** the `mgmtuplink` line note reads *"each rack's OOB switch uplinks to the
**spine-rack OOB** (1 per rack × 2)"* — but the B6 rule (2026-07-16) removed the
dedicated spine rack; there is no spine-rack OOB to aggregate to. The note cites
a rack the design no longer builds.

**Ruling (maintainer):** each rack's OOB switch uplinks to the customer's
**existing out-of-band / management network** (qty stays 1 per rack) — the
standard brownfield model; an isolated OOB island is wrong for an incremental
deal. A future greenfield deal with no existing mgmt network is a new question to
surface then, not a default to change now.

**Fix:** the `mgmtuplink` note now reads *"each rack's OOB switch uplinks to your
existing out-of-band / management network (1 per rack × N)"* — no invented
spine-rack aggregation switch. Regression-guarded in `tests/unit-engine.js`.
